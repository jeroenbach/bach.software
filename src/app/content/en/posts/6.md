Ever built a large form in Vue? Then you know how it goes: it starts as a handful of inputs and ends as a wall of markup, scattered `v-if` conditions and validation rules that slowly drift apart.
In this article I introduce [Vue Dynamic Form](https://vue-dynamic-form.bach.software/), a library I created to handle complex forms, without the complexity.

<!--more-->

The idea is simple: you describe **what** your form contains as plain metadata, and define **how** it looks in a single template component. The library handles everything in between: field paths, validation, repeatable sections, mutually exclusive branches and conditional behavior.

And there's a second reason I believe this approach matters right now: it makes forms something AI can generate reliably. More on that [later in this article](#why-this-matters-in-the-age-of-ai), but first let's look at the library itself.

## The problem with large forms

Most form libraries couple logic to markup. Every field means another block of template code: the input itself, its label, its error message, its required indicator. Add conditional fields, repeatable sections and cross-field dependencies, and your form component becomes hard to read, hard to test and even harder to keep consistent with the other forms in your application.

The result is that every form in your project ends up implementing the same things in slightly different ways: a different way of showing errors, a different spacing between fields, a different approach to "add another item".

## The idea: separate metadata from markup

Vue Dynamic Form splits a form into three parts:

- **Metadata** - a plain object tree describing the fields, their validation rules and their behavior
- **A template** - one component that defines how each field *type* is rendered
- **The `DynamicForm` component** - the engine that brings the two together, built on top of [vee-validate](https://vee-validate.logaretm.com/v4/)

The metadata model is inspired by **XSD** (XML Schema Definition), one of the most battle-tested formats for describing structured data. That heritage is what makes it possible to express almost any form scenario: nested groups, repeatable sections, mutually exclusive choices and conditional requirements, all in plain data.

The important part: you write the template **once**. It becomes your application-wide (or even organization-wide) definition of what a text field, a select, a section heading or a repeatable list looks like. After that, creating a new form is nothing more than writing metadata.

## Getting started

Install the library together with its peer dependencies:

```bash
pnpm add @bach.software/vue-dynamic-form vee-validate @vee-validate/rules vue
```

### Step 1: Define your field types

First you declare which field types exist in your application and which extra properties your fields can have. This lives in a plain `.ts` file, so pages and tests can import it without pulling in any components:

::code-group

```typescript [MyFormTemplate.ts]
import type { GetMetadataType } from '@bach.software/vue-dynamic-form';
import { defineMetadata } from '@bach.software/vue-dynamic-form';

export const metadata = defineMetadata<
  {
    // The field types and their value types
    text: string
    checkbox: boolean
    heading: never
  },
  {
    // The extra properties fields can have
    label?: string
    description?: string
    options?: { key: string, value: string }[]
  }
>();

export type Metadata = GetMetadataType<typeof metadata>;
```

::

### Step 2: Build your template

Next, you map each field type to your UI components. This is where your design system lives: labels, error messages, required indicators, spacing. All of it defined in one place:

::code-group

```vue [MyFormTemplate.vue]
<script lang="ts" setup>
import { DynamicFormTemplate } from '@bach.software/vue-dynamic-form';
import { metadata } from './MyFormTemplate';
</script>

<template>
  <DynamicFormTemplate :metadata-configuration="metadata">
    <!-- The wrapper around every field: label, error, required indicator -->
    <template #default="{ fieldMetadata, fieldContext: { errorMessage, label }, required }">
      <label :for="fieldMetadata.path">{{ label }} <span v-if="required">*</span></label>
      <slot />
      <span v-if="errorMessage.value">{{ errorMessage.value }}</span>
    </template>

    <template #heading="{ fieldContext: { label } }">
      <h3>{{ label }}</h3>
      <slot />
    </template>

    <template #text-input="{ fieldMetadata, fieldContext: { value, handleChange, handleBlur } }">
      <input
        :id="fieldMetadata.path"
        :value="value.value"
        @input="handleChange"
        @blur="handleBlur"
      />
    </template>

    <template #checkbox-input="{ fieldMetadata, fieldContext: { value, handleChange } }">
      <input
        :id="fieldMetadata.path"
        type="checkbox"
        :checked="value.value"
        @change="handleChange"
      />
    </template>
  </DynamicFormTemplate>
</template>
```

::

This minimal template covers text fields, checkboxes and headings. The live examples further down this article use a slightly bigger version of it - with slots for selects, repeatable fields and choices - which you can find [here on GitHub](https://github.com/jeroenbach/bach.software/blob/main/src/app/examples/post6/MyFormTemplate.vue). But remember: however big your template gets, you still only write it **once**.

### Step 3: Create forms with metadata only

From this point on, every form in your application is just data. Try it yourself in the **Preview** tab:

::code-group

```vue [MyPage.vue]
<script setup lang="ts">
import type { Metadata } from './MyFormTemplate';
import { DynamicForm, useDynamicForm } from '@bach.software/vue-dynamic-form';
import { ref } from 'vue';
import MyFormTemplate from './MyFormTemplate.vue';
import { settings } from './settings';

const { handleSubmit } = useDynamicForm();
const submitted = ref<string>();

const fields: Metadata[] = [
  {
    name: 'person',
    type: 'heading',
    fieldOptions: { label: 'Person' },
    children: [
      { name: 'firstName', type: 'text', fieldOptions: { label: 'First name' } },
      { name: 'lastName', type: 'text', fieldOptions: { label: 'Last name' } },
    ],
  },
];

const onSubmit = handleSubmit((values) => {
  submitted.value = JSON.stringify(values, null, 2);
});
</script>

<template>
  <form @submit="onSubmit">
    <DynamicForm :metadata="fields" :template="MyFormTemplate" :settings="settings" />
    <button type="submit">Submit</button>
  </form>
  <pre v-if="submitted">{{ submitted }}</pre>
</template>
```

::

Notice there is no markup per field anymore. The `person` group automatically becomes a path prefix, so the submitted values arrive as `values.person.firstName` and `values.person.lastName`. Both fields are required by default (just like in XSD, `minOccurs` defaults to 1) - hit submit without filling them in and see the validation kick in.

The `settings` import controls when validation runs and which error messages are shown; we'll get to it in the validation section below.

## Validation, the XSD way

Validation rules are part of the metadata as well. The `restriction` property translates directly into registered vee-validate rules:

```typescript
{
  name: 'username',
  type: 'text',
  fieldOptions: { label: 'Username' },
  restriction: {
    minLength: 3,
    maxLength: 20,
    pattern: '^[a-zA-Z0-9_]+$',
  },
}
```

Besides the string restrictions shown here, there are numeric ranges (`minInclusive`, `maxExclusive`, ...), `enumeration`, `fractionDigits`, `totalDigits` and more. Whether a field is required at all is controlled by `minOccurs`, just like in XSD.

When validation runs and what the error messages say is configured through a settings object. This is another thing you define once for your whole application:

::code-group

```typescript [settings.ts]
import type { DynamicFormSettings } from '@bach.software/vue-dynamic-form';

/**
 * Our application-wide form settings: validation timing and error messages.
 * Defined once, used by every form.
 */
export const settings: DynamicFormSettings = {
  // No errors while filling in, live feedback after the first submit
  validateOnValueUpdate: false,
  validateOnValueUpdateAfterSubmit: true,
  messages: {
    required: '{field} is required',
    minOccurs: 'Add at least {min} item(s)',
    choiceMinOccurs: 'Fill in at least {min} of these options',
    minLength: '{field} must be at least {length} characters',
    maxLength: '{field} may not exceed {length} characters',
    pattern: 'This is not a valid {field}',
  },
};
```

::

## Structure: groups, arrays and choices

This is where the XSD inspiration really pays off. Three structural concepts cover almost every complex form scenario I've encountered:

**Repeatable fields** - set `maxOccurs` greater than 1 and a field (or an entire group) becomes an array. The library manages the add/remove controls, occurrence tracking and minimum/maximum enforcement, and the values arrive as `values.contacts[0].name`, `values.contacts[0].email`, and so on.

**Mutually exclusive choices** - a field with `choice` presents several branches of which the user fills in exactly one. Once one branch gets a value, the siblings are disabled automatically.

**Optional groups** - set `minOccurs: 0` on a group and child validation is suspended until the user starts filling in values. Think of a "secondary contact" section: completely optional, but once you enter a name, the email becomes required too.

All three can be nested and combined: choice branches can be groups, groups can be repeatable, arrays can contain choices. Try that with hand-written `v-if` logic.

Here's a live form combining a repeatable contacts group with a choice. Add a few contacts, fill in one of the two contact options, or submit an empty form to see the occurrence validation:

::code-group

```vue [MyForm.vue]
<script setup lang="ts">
import type { Metadata } from './MyFormTemplate';
import { DynamicForm, useDynamicForm } from '@bach.software/vue-dynamic-form';
import { ref } from 'vue';
import MyFormTemplate from './MyFormTemplate.vue';
import { settings } from './settings';

const { handleSubmit } = useDynamicForm();
const submitted = ref<string>();

const fields: Metadata[] = [
  {
    name: 'contacts',
    fieldOptions: { label: 'Project contacts' },
    minOccurs: 1,
    maxOccurs: 3,
    children: [
      {
        name: 'name',
        type: 'text',
        fieldOptions: { label: 'Name' },
        restriction: { minLength: 2 },
      },
      {
        name: 'email',
        type: 'text',
        fieldOptions: { label: 'Email' },
        restriction: { pattern: '^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$' },
      },
    ],
  },
  {
    name: 'contactMethod',
    fieldOptions: { label: 'How should we reach you?' },
    minOccurs: 1,
    choice: [
      { name: 'email', type: 'text', fieldOptions: { label: 'Email address' } },
      { name: 'phone', type: 'text', fieldOptions: { label: 'Phone number' } },
    ],
  },
];

const onSubmit = handleSubmit((values) => {
  submitted.value = JSON.stringify(values, null, 2);
});
</script>

<template>
  <form @submit="onSubmit">
    <DynamicForm :metadata="fields" :template="MyFormTemplate" :settings="settings" />
    <button type="submit">Submit</button>
  </form>
  <pre v-if="submitted">{{ submitted }}</pre>
</template>
```

::

::

Notice what you did *not* have to write: no `v-for` over the contacts, no add/remove state management, no logic to disable the phone field once an email address is entered. That's all driven by `minOccurs`, `maxOccurs` and `choice`.

## Dynamic behavior with computedProps

Real forms react to their own state: a VAT number that only applies to business accounts, city options that depend on the selected country. Instead of scattering watchers around your component, each field carries its behavior right next to its definition via `computedProps`.

In the example below, switching the account type to "Business" enables the VAT number field, makes it required and removes the hint - all from three lines of metadata:

::code-group

```vue [MyForm.vue]
<script setup lang="ts">
import type { Metadata } from './MyFormTemplate';
import { DynamicForm, useDynamicForm } from '@bach.software/vue-dynamic-form';
import { ref } from 'vue';
import MyFormTemplate from './MyFormTemplate.vue';
import { settings } from './settings';

const { handleSubmit, useFieldValue } = useDynamicForm();
const submitted = ref<string>();

// Subscribe to the accountType field, so we can use it in computedProps
const accountType = useFieldValue('accountType');

const fields: Metadata[] = [
  {
    name: 'accountType',
    type: 'select',
    fieldOptions: { label: 'Account type' },
    options: [
      { key: 'personal', value: 'Personal' },
      { key: 'business', value: 'Business' },
    ],
  },
  {
    name: 'vatNumber',
    type: 'text',
    fieldOptions: { label: 'VAT number' },
    computedProps: [
      (field) => {
        const isBusiness = accountType.value === 'business';
        field.disabled = !isBusiness;
        field.minOccurs = isBusiness ? 1 : 0; // only required for business accounts
        field.description = isBusiness
          ? undefined
          : 'Only applicable to business accounts';
      },
    ],
  },
];

const onSubmit = handleSubmit((values) => {
  submitted.value = JSON.stringify(values, null, 2);
});
</script>

<template>
  <form @submit="onSubmit">
    <DynamicForm :metadata="fields" :template="MyFormTemplate" :settings="settings" />
    <button type="submit">Submit</button>
  </form>
  <pre v-if="submitted">{{ submitted }}</pre>
</template>
```

::post6-example3{label="Preview"}
::

::

Each `computedProps` function runs inside a Vue `computed()`, so it only re-runs when the values it reads actually change. You can update select options on the fly, change validation rules, hide fields, or even make a parent group collapse when all of its children are hidden. The [documentation](https://vue-dynamic-form.bach.software/guide/dynamic-fields) covers these patterns in detail.

## <span id="why-this-matters-in-the-age-of-ai">Why this matters in the age of AI</span>

Now to the part I hinted at in the introduction. We all use AI coding assistants more and more, and forms are a task we love to delegate: they're tedious, repetitive and time-consuming. But if you've ever asked an AI to build a large form component, you know the result: hundreds of lines of markup, ad-hoc validation, conditional logic spread across the template, and subtle differences from the forms it generated yesterday. AI is powerful, but it needs guidance and constraints.

Vue Dynamic Form provides exactly those constraints, because of how the responsibilities are split:

- **The logic lives in the library.** Path resolution, validation, array handling, choice exclusivity, reactivity - none of it is generated, so none of it can be hallucinated. It's the same battle-tested code in every form.
- **The template is your guardrail.** You (or your organization) define once how a text field, a select or a repeatable section looks and behaves. The AI doesn't get to reinvent your design system with every prompt: it can only use the field types you defined.
- **The AI only generates metadata.** And that's the part AI is genuinely great at: transforming a requirement ("build an onboarding form with company details, up to five contacts, and either an email or a phone number") into structured, declarative data.

In practice, my prompts look like this:

```
Look at MyFormTemplate.ts for the available field types and extra
properties. Now create the metadata for a client onboarding form:

- Company details: name (required), VAT number (only enabled for
  business accounts), industry
- Project contacts: 1 to 5 contacts with name, email and role
- Preferred contact method: either email or phone, exactly one
```

Because the output is a typed `Metadata[]` array, TypeScript immediately flags any field type or property that doesn't exist in your definition. And reviewing the result is nothing like reviewing 400 lines of generated template code: you read a small tree of field definitions and check it against the requirements, the same way you would review a config file.

This scales beyond a single project. Define one template per design system and every project in your organization creates forms the same way: consistent in look and behavior, whether the metadata was written by a developer or generated by AI. The form definitions themselves are so close to plain JSON that you can even store them in a database and serve them at runtime.

## Final thoughts

Vue Dynamic Form came out of years of building the same kind of complex forms over and over: insurance forms, onboarding flows, configuration wizards. The pattern that survived was always the same: keep the structure declarative, keep the rendering centralized, and let a well-tested engine do the wiring.

What I didn't anticipate when I started is how well this pattern fits the way we build software today. A declarative metadata format with the logic safely tucked away in a library turns out to be the ideal contract between a developer, a design system and an AI assistant.
