# Story: Show failed page-reads and page-likes fetches to the visitor (FE-19)

## Decided without the maintainer (research)

Settled from research during story prep (adversarial review adoption), not reviewed by the maintainer. Override any of these freely.

## Functional
### User story
As a site visitor, I want a clear, translated, dismissible message when the page-reads or page-likes data cannot be loaded, so that I know something went wrong instead of silently seeing a missing counter, and so that Jeroen's backend failure classification (502 vs 500) results in the right visitor-facing message.

### Test-infrastructure facts the developer must act on

1. **The new tests would not run as the Vitest include globs stand.** `vitest.config.ts` only includes `components/`, `composables/`, `contexts/`, `utils/` (and `tests/nuxt/` for the nuxt project). `src/app/errors/` (where the adopted contract spec sits next to `error-codes.json`) and `src/app/types/` (where the reconciled `problemDetails.ts` guards live) are in no include list, so a spec there silently never runs and the "fails when a code lacks a translation" guarantee would be vacuous. Plan: add `src/app/errors/**/*.{test,spec}.{ts,js}` and `src/app/types/**/*.{test,spec}.{ts,js}` to the `unit` project include (and `src/app/types/**` to the coverage include so the guards count). `vitest.config.ts` is therefore a modified file of this story, not listed in the Architecture reference.
2. **The existing context tests call the composable outside any component.** `usePageLikesContext.nuxt.test.ts` and `usePageLikesContext.test.ts` call `usePageLikesContext()` directly. After the change `useApiState` pulls in `useI18n` (outside a component setup it throws), `useMessageStore` (needs an active Pinia) and `tryOnUnmounted`. Both files must be updated: the unit file gets `setActivePinia(createPinia())` plus `vi.mock('vue-i18n', ...)` (or a mocked `useI18n` matching how the developer imports it; `mockNuxtImport('useI18n')` only works for the auto-import form); the nuxt file wraps calls in a small host component (the pattern the existing "after mount" test already uses) so lifecycle hooks have an owner.
3. **There is no `usePageReadsContext` test today.** One is added (`usePageReadsContext.nuxt.test.ts`), covering success, the plausible-domain rewrite and every error path; this also lifts coverage.
4. **Hand-built error objects are not enough.** Kiota's generated models type `errors` as `ValidationProblemDetails_errors { additionalData }` and put extensions (`code`, `placeholders`) in `additionalData`, and the JSON parse node may hand back untyped wrappers instead of plain strings/arrays. The reference `toProblemDetails` does `Object.entries(problem.errors)` and `for (const code of codes)`, which on Kiota's real shape would iterate `['additionalData', {...}]` and throw. A mocked client rejecting with a literal object can pass while production fails. So one test drives the real generated client (see "Real-adapter test" below).
5. **Hydration trap in the outlet.** The reference `MessageBarContext.registerOutlet` creates the outlet id with `crypto.randomUUID()` during setup and `MessageBarOutlet` renders it as `data-message-outlet`. The site is prerendered, so the server HTML carries uuid A and the client registry creates uuid B; Vue does not patch attribute mismatches on hydration in production, so the `Teleport to="[data-message-outlet='B']"` finds no target and the bar never appears on the live site, while every component test (client-only mount) passes. Only the Playwright test against the built static site (below) catches this. If it fails, the developer must make the id deterministic across server and client (for example `useId`/a counter).
6. **Late reports after unmount.** The reference `addMessage` awaits `nextTick` before pushing. A request that fails after the visitor navigated away (the reporting component already unmounted, `clearInstance` already ran) would push a message owned by a dead instance that nothing ever clears, so a stale error bar shows on an unrelated page. Planned as an explicit regression test (below); if it fails, the developer drops messages whose instance is already cleared.

Deviations and decisions:
- **`isApiError` does not require `instanceof Error`.** Kiota throws the plain parsed error model (not an `Error`) for statuses that have an error mapping, with `responseStatusCode` set; the reference guard would have returned undefined for every 400/500/502 body. Found by the real-adapter test. Unmapped statuses throw a `DefaultApiError` (an `Error`), which also has the status.
- **Status comes only from `responseStatusCode`**, never from the body `status`.
- **Validation heading:** the reporter shows `errors.validation` ("validation pass-through bucket") as the bar heading for a validation problem without a top-level code, because the backend's FluentValidation 400 carries no `code`; each field line is still a translated code. Same adaptation keeps `errors.unexpected` for everything else.
- **Duplicate handling chosen: `addOnce` in the reporter.** The store's `addOnce` identity widened to severity + description + details (JSON compare), so two identical validation bars also collapse, while different details stay separate. Grouping stays available through the options but is not used.
- **Late report after unmount (dropped):** the store tracks disposed instances (unmounted owners) and ignores non-persisted messages from them. Explicit `clear()` (used by retry) does not dispose. Persisted messages (success, info, warning) are still kept so a closing dialog keeps its confirmation.
- **Outlet ids are counters scoped to the `MessageBarContext` instance** (`messageOutlet0`, `message0`), not `crypto.randomUUID()`, so the prerendered markup and the client registry agree (hydration). Confirmed in the Playwright run.
- **Outlet CSS:** the sticky and fixed outlets use `top-16` (header max height, 64px) instead of the undefined `--app-header-height` variable, and the fixed outlet drops `min-h-full`. Please check placement in M7.
- **`MessageBar` look:** in-flow bars use the `AlertBar` palette, `fixed` bars the `NotificationMessage` card (left accent, shadow, dark mode); the close label is `$t('messageBar.close')` (new key, translated in all three locales).
- **`useNotificationStore.addError` removed** (with its three tests and the `notification.error.unknown` locale key). It was the only user of the old `~/types/ApiError|ProblemDetails|ValidationProblemDetails` guards, had no production caller, and keeping it would have kept the parallel old type set. The three old type files are deleted; `~/types/problemDetails.ts` replaces them. On a case-insensitive filesystem git reports `ProblemDetails.ts` as modified rather than deleted plus added.
- **`usePageReadsContext` returns `mappedState`** with `mapData: data => data ?? undefined`, because a failed call resolves to null and the page prop is `PageReads | undefined`.
- **Retry overlapping an in-flight call:** not specified by the reference; left as last-write-wins.
- **`useI18n` is imported from `vue-i18n`** in the composables (as in the reference), so they are unit-testable with `vi.mock('vue-i18n')`; the nuxt tests use the real i18n.
- **Shared test helpers** in `src/app/tests/helpers/` (`apiErrors.ts` with `kiotaError`/`deferred`, `translate.ts`, `mountWithContexts.ts`), reused by more than three files.
- `src/app/errors/errorsCatalog.spec.ts` checks all three locales and equal placeholders; `vitest.config.ts` and `package.json` (`--exclude errors`) changed as the story says. `specs/enforcement.md` FE-19 row and `specs/components.md` updated.

Findings for the maintainer (not fixed here):
- **A 502 or 503 that carries a non-JSON body is not recognised as unavailable.** Kiota throws a plain `Error` ("content type text/html does not have a factory registered", no `responseStatusCode`) when the content type has no parse node, so an HTML 502 from an ingress or proxy surfaces as `errors.unexpected`. Only JSON problem responses map to `errors.unavailable`. A fix belongs in `useApiClient` (not generated), for example a fallback parse node, and is outside this story.
- **A 503 is retried by Kiota's default retry handler** before the error surfaces, so the unavailable message appears after the retry delays (several seconds). The reporter mapping itself is covered by unit tests; the real-adapter test therefore has no 503 case.
- **The CI static server has no backend.** The existing page baselines stayed identical in the Docker run, so no `page.route` stub was needed in `pages.spec.ts`.

Grep shows no remaining consumer (`CodeGroup.vue` and `AppHeaderContext.vue` only use `add`; `AppHeader`/`AlertBar`/`NotificationMessage` only import the `Notification` type), and nothing else used the old type guards. ST-06 should treat that item as done, not re-do it. This is a mild pre-emption of ST-06 but it was forced by deleting the old type set (AC 10) and leaves ST-06 AC 15 inputs (`useMessageStore` with numeric `closeIn`) ready.
- Validation heading `errors.validation`, `addOnce` duplicate handling, dropped late reports, counter-based outlet ids, `top-16` instead of the undefined `--app-header-height`: all justified by the QA plan's own facts and verified (hydration and placement seen).
- HTML 502/503 surfaces as `errors.unexpected`: does not contradict any criterion. AC 5 and AC 14 key on the backend answering with a problem response carrying a `responseStatusCode`. Verified in the Kiota source: the client now declares a 502 mapping, so an HTML body hits `getRootParseNode` and throws a plain `Error` with no status. Recorded as a follow-up, not a fail.
