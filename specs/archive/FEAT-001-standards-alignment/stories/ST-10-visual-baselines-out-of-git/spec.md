## Functional
### User story
As Jeroen (the maintainer), I want visual baselines stored in object storage and compared per pull request, so that the repository stops carrying about 40MB of binary PNGs (a 248MB pack), updating a baseline no longer needs a snapshot commit, and approving the PR is approving the visual change.

### Findings that change the plan (flagged, not silently accepted)

1. **Live data would make the page captures flaky, and after ST-05 would capture an error bar.** `pages/[[segment1]]/[id]-[[slug]].vue` calls `usePageReadsContext`/`usePageLikesContext`, which hit the real API (`pr-<n>.api.bach.software` in CI). `post2-page` therefore renders live read and like counts, and once ST-05 lands an unreachable API renders a `MessageBar` into the screenshot. The standard requires fixture data. Plan: the capture helper stubs the analytics routes with `page.route` returning constants (and the stub must also satisfy the 502/error-free path), so counts are fixed and no bar appears. Not covered by any acceptance criterion as written; propose adding it to AC1 ("data is fixture data, not live backend").
2. **A red reg-suit check is a commit status, not a job failure.** `reg-suit run` reports diffs through `reg-notify-github-plugin` as a commit status; whether the workflow job itself exits non-zero on a diff is unverified. AC9 says "the check is red", so the manual verification must confirm which signal turns red (the reg-suit status context, the job, or both) and record it. If the maintainer wants a blocking check, that is branch-protection configuration and possibly an extra step, not covered by the plan. Flag in Implementation notes.
3. **PR checkout is a synthetic merge commit.** On `pull_request` events `actions/checkout` checks out `refs/pull/<n>/merge`, so the commit hash the git-hash plugin keys the PR run under, and the SHA the notifier posts the status to, may not be the PR head SHA. Verify on the first PR run (manual step M4) that the status lands on the PR head commit and that the merge-base lookup finds the `main` baseline; if not, check out `github.event.pull_request.head.sha`.
4. **Git inside the container.** The capture and `reg-suit run` run in `mcr.microsoft.com/playwright:v1.60.0-jammy` as root against a checkout owned by another user. The git-hash plugin shells out to git, which can fail with "dubious ownership" unless `git config --global --add safe.directory "$GITHUB_WORKSPACE"` is set (the removed `30-update-snapshots.yml` did exactly this), and git must exist in the image. Verify early in the first CI run (M3).
5. **Missed references to retire.** Beyond the files listed in the Architecture reference, these also mention the old flow and must be updated or the grep in M7 fails: `README.md` (lines about `ci:playwright:docker` and `ci:playwright:docker:update`), `scripts/check.sh` (interactive "update the snapshots" branch calling `pnpm ci:playwright:docker:update`), and the Commands block of `specs/PROJECT.md` (`pnpm playwright:docker:update`). AC10 only names the Testing section; propose widening it to the whole file.
6. **`sitemap.xml.spec.ts` still uses `toMatchSnapshot` against `sitemap.xml.spec.ts-snapshots/sitemap-chromium-linux.xml`.** That is a text snapshot, not a PNG, so AC5 (delete PNGs) must not delete the directory or that file, and the retired hook's pattern (`.png|.jpg`) never covered it. Calling this out so the cleanup does not break the sitemap test.
7. **Vague criteria, rewrite proposals.** AC2 "thresholdRate at or near zero": make it exactly `0` unless the determinism run (M2) proves a nonzero value is needed, then state the value and the reason. AC4 "documented": make it verifiable as "Implementation notes contain the numbered seeding steps (merge, let the `main` run finish, confirm the bucket prefix, open a PR, expect zero new)". AC9 "the check is red": see finding 2.
8. **Concurrency can drop a `main` publish.** The workflow has `cancel-in-progress: true` per ref, so two quick pushes to `main` can cancel the first run and never publish its snapshots. Whether the git-hash plugin falls back to the nearest ancestor that does have published snapshots is not verified here; check during M5 and, if it does not, exclude `main` from cancellation. Flag in Implementation notes.

## Adversarial review

Lite, story-level (blockers first). Verified against the workflows, the Playwright specs/config, `package.json`, `scripts/check.sh`, `README.md`, `.claude/hooks/block-snapshot-image-edits.sh`, `vitest.config.ts`, `usePageReadsContext.ts`, and the reg-suit / AWS SDK docs.

1. **(should-fix) The reg-suit S3 config in AC2 uses AWS SDK v2 option names, but the current `reg-publish-s3-plugin` passes `sdkOptions` to an AWS SDK v3 `S3Client`.** AC2 (mirroring the feature's DECIDED ADR 5-A) specifies `s3ForcePathStyle: true` and `signatureVersion: 'v4'`. Those are AWS SDK **v2** `S3` constructor keys. The current `reg-publish-s3-plugin` documents `sdkOptions` as "options to pass to `S3Client`" (the `@aws-sdk/client-s3` v3 client), where the path-style key is `forcePathStyle` (no `s3` prefix) and `signatureVersion` does not exist (SigV4 is the only, default scheme). As written, the v2 keys are silently ignored: `s3ForcePathStyle` does nothing (addressing falls back to virtual-hosted) and `signatureVersion` is dead config. It will likely still publish (R2 supports virtual-hosted-style for a DNS-safe bucket name like `bach-software-visual-regression`, and recent SDK v3 auto-forces path style for a custom `endpoint`), which is why this is should-fix rather than blocker, but the config does not do what the spec believes and omits `region: 'auto'`, which SDK v3 requires for R2. PROPOSED resolution below. Because this contradicts the DECIDED ADR 5-A, it needs a maintainer amendment of the feature spec, not a silent story-local override (hard rule 4), so it is left for discussion.

   PROPOSED (adversarial review): amend the feature's ADR 5-A DECIDED provisioning entry and this story's AC2 to describe v3-shaped `sdkOptions`: `endpoint` built from `CLOUDFLARE_ACCOUNT_ID`, `forcePathStyle: true`, `region: 'auto'`, and drop `s3ForcePathStyle` and `signatureVersion`. Keep credentials out of the file (the SDK default chain reads `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` from the environment). Alternatively, if the maintainer intends to pin an older `reg-publish-s3-plugin` that still uses SDK v2, state the pinned version in the Architecture reference devDependency list so the v2 keys are correct. Either way the `regConfig_*` guard (AC2 mapping) must assert the keys that match the installed SDK major, not v2 keys against a v3 client.

   DECIDED (research): Adopt the PROPOSED correction with the current plugin (no older pin). AC2 and the ADR use the SDK v3 `S3ClientConfig` keys: `endpoint`, `forcePathStyle: true`, `region: 'auto'`; `s3ForcePathStyle` and `signatureVersion` are dropped, and credentials stay out of the file. The `regConfig_*` guard asserts these keys.

### Judgment of the developer's deviations

1. **Report link with `customDomain` unset. Claim verified; needs the maintainer.** `reg-publish-s3-plugin` source (`reg-viz/reg-suit` `packages/reg-publish-s3-plugin/src/s3-publisher-plugin.ts`, same in installed 0.14.4 `lib`): `publish()` builds `https://${getBucketDomain()}/${key}/index.html`, and `getBucketDomain()` returns `customDomain` or else `${bucketName}.s3.amazonaws.com`. `customDomain` is used for nothing else; the S3 client is built only from `sdkOptions`. (b) leave it unset as the DECIDED entry says and accept a broken link (reports would then have to be opened by hand from the `r2.dev` URL plus commit-hash path). Option (a) contradicts the binding DECIDED text, so it needs an amendment to ADR 5-A and AC2 by the maintainer. Either way, confirm in M3.
