## Functional
### User story
As Jeroen (the maintainer), I want every reusable presentational component to appear in Storybook with one story per meaningful state, and each story visually regression-tested, so that I can see and verify the full capability of the UI components without navigating the app and so that a styling regression in any state is caught.

### Acceptance criteria
1. Given the then-current tree, then the coverage gap is re-measured first (the spec says 24 of about 39 presentational components have no story and 13 existing story files; the retired `AlertBar`, `AlertBarContainer`, `NotificationMessage` and `NotificationContainer` are gone and are not storied) and the measured list is written into Implementation notes.
2. Given each presentational component without a story (for example `App404`, `AppBackground`, `AppButton`, `AppChip`, `AppError`, `AppIcon`, `AppImage`, `AppMarkdown`, `AppProse`, `AppTransition`, `AuthorInformation`, `BlogPostFilter`, `BlogPostPagination`, `BlogPostSummary`, `BlogPosts`, `ColorModeSwitcher`, `LanguageSwitcher`, `PageContent`, `SearchButton`, `SearchModal`, `ShareOn`, `TableOfContentsList` and the final list from criterion 1), then a co-located `ComponentName.stories.ts` exists with a `Default` story plus one named story for each meaningful state the FE-13 standard lists (variants, data states, async/status states, interaction states, slots with and without content).

### Edge cases
- Components relying on Nuxt features (NuxtLink, NuxtImg, i18n) render in Storybook through the existing decorators; a story that cannot render without a context component is a sign the component is not presentational and is flagged rather than given a mock context.
- Stories must not depend on live backend data or the current date.
- Components that only wrap a slot (`AppProse`, `PageContent`, `BlogPosts`) get a story with representative slot content, not an empty frame.
- If a story id collides with an existing baseline name in the R2 bucket, the new name wins and the old one is cleaned up by lifecycle.

### Out of scope
- Stories for retired components, and for context components.
- Behaviour or markup changes to components to make them storyable beyond what is needed for isolation (flag instead).
- Changing the capture mechanism (ST-10).

## QA plan

### Approach
The deliverable is stories, so the primary "tests" are the stories themselves plus their visual-regression registrations. Three automated layers guard them, and a short manual checklist covers what cannot be automated.

1. **Guard test (Vitest, `unit` project)** in `src/app/tests/storybook/storybookCoverage.test.ts`. It reads the filesystem and keeps the story set honest (details in the mapping table). Needs one added include glob (`src/app/tests/storybook/**/*.{test,spec}.ts`) in the `unit` project of `vitest.config.ts`, because the unit project currently only includes `components`, `composables`, `contexts` and `utils`. Where possible it derives ids with Storybook's own helpers (`toId`, `storyNameFromExport` from `storybook/internal/csf`) instead of re-implementing the kebab rules.
2. **Visual capture (`components.spec.ts`, pinned jammy container)**, one registration per story id. The registration helper also fails the story on `pageerror`, on any console `error`, and on any `[Vue warn]` message, which is what "renders without console errors" (criterion 10) means in a machine-checkable form. This is an assertion added to the existing per-story test, not a change to the capture mechanism.
3. **reg-suit report on the PR** (manual read, criterion 8).

### Flags that change the work (resolve before or during implementation; none is silently accepted)
- **F1. Storybook cannot resolve `useI18n`, `useSeoMeta` or `NuxtLink` today.** Auto-import in `.storybook/vite.config.ts` covers only `vue` plus `utils`/`composables`; `preview.ts` stubs `NuxtLinkLocale` but not `NuxtLink`. Affected: `SearchButton` and `App404` (`useI18n`), `AppError` and `App404` (`useSeoMeta`), `SearchModal` and `BlogPostPagination` (`NuxtLink`, which would render as an unknown element with no anchor, a silent wrong render). Plan: add `useI18n` (from `vue-i18n`) to the auto-import list and a `NuxtLink` stub in `preview.ts`; these are inert and count as the "Storybook config" the architecture allows. `useSeoMeta` writes to the document head, which is a side effect, so per the edge case `AppError`/`App404` are either given an inert `useSeoMeta` no-op mock (one line in `.storybook/mocks/imports.ts`, same pattern as `useColorMode`) or flagged as not presentational and excluded with a reason in Implementation notes. Maintainer to confirm the choice; the guard test carries an explicit, reasoned exclusion list so nothing is skipped silently.
- **F2. `CodeGroup` and `PageReadProgress` are not cleanly presentational.** `CodeGroup` calls a message store and `useClipboard`; `PageReadProgress` runs `useReadProgressTracking` (timers and scroll listeners, so non-deterministic). Both fall under "flag, do not mock a context". Plan: flag both in Implementation notes and exclude with a reason; `PostImage` is storyable. If ST-06 reworks them into props-only components, story them then.
- **F3. Portaled and teleported components break the light/dark decorator.** The global decorator renders every story twice (a light wrapper and a `.dark` wrapper) and `dark:` styles key off an ancestor `.dark`. `SearchModal` and the `AppHeader` mobile menu use a headlessui `Dialog`, which portals to `body`, outside the `.dark` wrapper, and two open dialogs also fight over focus and `inert`. `MessageBarOutlet` stories teleport `MessageBar` to `[data-message-outlet='main']` and two outlets with the same name make the second wrapper receive nothing. Plan: these stories (`SearchModal` open states, `AppHeader` `MobileMenuOpen`, all `MessageBarOutlet` stories) are registered single-theme (`globals=theme:light` and `globals=theme:dark` as two entries, id suffix `-light` and `-dark`). For the portaled dialogs, dark only works if the decorator also toggles `dark` on `<html>` in single-theme mode; that is a decorator change (allowed by the architecture reference). If the maintainer prefers not to touch the decorator, the dark variant of those two components is recorded as a known gap. `MessageBar` itself, rendered in place with `teleport: false`, is not affected and uses the normal both-themes capture.
- **F4. Criterion 3 asks for "with and without a title", but the adopted `MessageBar` (FE-19 reference) has no `title`.** Its content is `description`, optional `details` rows, or the default slot. Verify against the final ST-05 component. If there is no title prop, reword to "with description only, with details, and with slot content" (the plan below uses that). If ST-05 added a title, add the two title stories.
- **F5. Interaction states need `play` functions or are limited to prop-driven states.** There are no `play` functions today. `AppHeader` `MobileMenuOpen` has no prop; its state is an internal ref. Plan: use a `play` function importing `userEvent` from `storybook/test` (bundled with Storybook 10, no new dependency) that clicks the open-menu control (select by the FE-07 test id from ST-09, never by text), at a mobile viewport via the story `parameters`. The capture helper must wait for the play function to finish before screenshotting (Storybook sets completion state on the preview; wait on it, no fixed timeouts). If that wait cannot be added without changing the ST-10 mechanism, drop `MobileMenuOpen` and flag it. Scroll-driven header shrink is not storyable (driven by `window` scroll via CSS animation delay) and is consciously excluded.
- **F6. Image volume and run time.** `components.spec.ts` runs in five Playwright projects (chromium, firefox, webkit, Pixel 5 / Mobile Chrome, iPhone 12 / Mobile Safari, defined in `playwright.config.ci.ts`): the 14 currently registered story ids correspond to the 70 baselines measured (14 × 5). Of the 90 new states, 10 are single-theme stories that each register twice (a `-light` and a `-dark` entry per F3): `SearchModal` 6, `MessageBarOutlet` 3, `AppHeader` `MobileMenuOpen` 1. So the new work is 80 both-theme registrations + 20 single-theme registrations = **100 new registrations**, which at five projects is **about 500 new images** (not the ~450 the earlier id-count figure gave; it undercut the single-theme pairs by ~50). At chromium + one mobile project it would be about 200. All run with `workers: 1` on CI.

### UI states policy for this slice
Every story must be assertable in these states where the component supports them: empty (`Empty`, `NoCategories`, `NoResults`), loading (`SearchModal` `Loading`), error/unavailable (`SearchModal` `Unavailable`, `MessageBar` `Error`), validation (`MessageBar` `WithDetails`), long or overflowing content (`LongText`, `LongTitle`, `LongName`, `ManyResults`, `ManyCategories`), and slot with and without content. Components without a state in one of these classes simply have no such story.

### Stack-specific regression classes
- Reactivity and render counts: not touched (stories add no runtime code); `AppHeader` `MobileMenuOpen` relies on an internal ref, so assert it through the play function, not by poking internals.
- Async cancellation: not applicable; no async code is added. The `play` function wait in F5 must not use a fixed timeout.
- State migrations: not applicable.
- Teleport and portal behaviour is the real regression class here (F3); it is covered by the single-theme registrations and the zero-warning assertion.

## Implementation notes
Filled by developer during implementation: deviations from plan and why. Deviations that affect the feature design/architecture are also propagated to the feature spec.

### Measured gap (AC1)
The tree has 40 `.vue` files under `src/app/components/`, 11 story files at the start (not 13: `AlertBar` and `NotificationMessage` stories are gone with their components). 29 components had no story. Excluded with a reason (guard test carries the list): `CodeGroup` (message store and clipboard), `PageReadProgress` (timers and scroll listeners), and the four `content/post1|post2/Post*Example*` wrappers (post-specific embeds of demos from `src/app/examples`, not reusable components). ### Decisions on the flags
- F1: `useI18n` added to the Storybook auto-imports, `useSeoMeta` is an inert mock (`mocks/useSeoMeta.ts`, also exported from `mocks/imports.ts`), and a `NuxtLink` stub (`mocks/NuxtLink.vue`) is registered, also for `NuxtLinkLocale` so object `to` values (query links) get a real `href`. String hrefs are unchanged.
- F2: `CodeGroup` and `PageReadProgress` excluded as flagged.
- F3: stories whose content portals or teleports set `parameters.singleTheme` (`SearchModal`, `MessageBarOutlet`, `AppHeader` `MobileMenuOpen`). The decorator shows light for these when the theme is `both`, honours an explicit `theme:light|dark` global, and toggles `dark` on `<html>` in single dark mode. Story-level `globals` was tried first and rejected: it overrides the URL global, so the dark capture stayed light. The capture registers these as `<name>-light` and `<name>-dark`.
- F4: AC3 reworded (no title prop); stories are `Default`, `Success`, `Error`, `Warning`, `Info`, `WithDetails`, `WithSlotContent`, `NotClosable`. No `Closed` or `closeIn` story (time dependent). Fixed and sticky outlets are not storied (viewport relative, not deterministic inside the decorator frame).
- F5: `MobileMenuOpen` uses a play function (`userEvent.click` on a test id, then waits for the dialog). `AppHeader` had no id on the open-menu button, so `data-testid="header-open-menu-button"` was added (markup change needed for the play function). The Storybook iframe has no viewport toolbar, so the registration carries a `viewport` (390x844) that the spec applies before navigating. The capture helper waits for the preview render phase (`completed` or `finished`), no fixed timeouts.
- F6: all five Playwright projects kept. 128 registrations x 5 = 640 captures (12 pre-existing ids, 116 new; 9 of the new ones are existing stories that were never registered, see below).
- F7: existing titles and ids unchanged; new files use `Elements/` or `Components/`. Capture names strip the sidebar prefix (`appbutton--default`), which keeps the existing names (`footer--default`) pairing with their baselines.
- F8: `**/*.stories.ts` added to `coverage.exclude`; `autoUpdate` rewrote the thresholds in `vitest.config.ts` (coverage now statements 87.9, branches 80.96, functions 87.59, lines 88.16).

### Deviations from the plan
- The registration list lives in `src/app/tests/playwright/componentStories.ts` (data only) and `components.spec.ts` loops over it, so the guard test can import the ids instead of parsing the spec.
- The guard requires every story export to be registered, so pre-existing unregistered stories were registered too: `footer--short`, `blogpost--liked`, `likebutton--without-count`, four `responsiveimage--*`, two `tableofcontents--*`.
- AC2 wants a `Default` in every file, so matrix names moved: `ColorModeSwitcher` `System`, `LanguageSwitcher` `English`, `BlogPostPagination` `FirstPage`, `SearchModal` `Idle` and `MessageBarOutlet` `SingleMessage` are now `Default`.
- Extras beyond the matrix: `AppChip` `Blue`, `BlogPostSummary` `WithImagePosition`, `AppLink` `Plain` and `NewTab`.
- Fixtures were lifted into `src/app/tests/storybook/fixtures/` (CV, portfolio, blog post summaries, table of contents); existing `Default` stories keep their content.
- The capture helper additionally fails on `pageerror`, console errors and `[Vue warn]`.

### Findings flagged, not fixed
- `MessageBar` `details`: each row is an `inline-flex` list item, so two rows run together on one line ("Url: The url is required.Name: ..."). The `WithDetails` story captures that as is; a layout fix belongs to the component.
